* **OpenCode V2 runs DAW's gates.** The OpenCode plugin now also speaks V2's interface, from the same file: a write a phase forbids is refused before it lands (through `write`, `edit`, `patch` and a namespaced id), a state forged behind it is reported in the result of the tool that follows, the user's turns are counted, and the bootstrap, the post-compaction reminder and the packaged skills reach the model as they do under V1. Under V2 every read-only DAW agent gets `edit: deny` and `shell: ask` in V2's `permissions` format, and a plugin install gains the `daw-module-verifier` it ships no file for. V1 loads and behaves as before. OpenCode's `apply_patch` now names its files to the gate, so a patch to product source in a phase that forbids it is refused where it was let through unjudged. A drop-in's bootstrap now points the model at `.daw/orchestrator.md` and no longer tells it not to install the DAW it installed, and `.opencode/INSTALL.md` counts what the drop-in writes (20 skills, 5 agents, 20 commands) and says how it starts under V1 and V2. Driven live, the published V2 build (`opencode-ai` 0.0.0-dev-202610280534) gives a plugin no tool or session hook yet: its own session runtime applies the agents' permissions and starts a drop-in through `AGENTS.md`, but no gate runs there until V2 offers those hooks (`scripts/acceptance.md`), and the plugin says so on stderr when it loads under a V2 build without them. A `path` beside a patch's `patchText` no longer hides the files the patch writes: both are judged. Claude Code's drop-in hook commands quote their path (`bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/…"`), so DAW's hooks run in a repo whose path has a space, where they used to run nothing; the next install replaces the unquoted blocks, and an uninstall recognises them as DAW's.
